## تخصص لاراول

**middleware ها را در لاراول توضیح دهید.**
- از الگوی Chain of responsibility برای پیاده سازی آنها استفاده شده است
- در خواست های http را دریافت کرده و شروطی را بررسی می کند و در صورت تمایل اجازه ادامه کار یا قطع جریان و تغییر مسیر را می دهند
- مثلا برای تشخیص لاگین بودن یا نبودن کاربران استفاده می شود (روی روت های خاص خودش)
- مثلا مقادیر input فرم ها را trim می کنند (که خود لاراول زحمتشو کشیده برامون و این میدل ویر رو تعریف کرده)
- میدلویرها میتونن گلوبال باشن، می تونن برای یه گروه از روت ها استفاده بشن، میتونن برای یه روت خاص تعریف کنیم و استفاده کنیم
- مثالی از تعریف میدلویر: php artisan make:middleware IsAdmin

**چطور می‌تونیم از Validation ها استفاده بکنیم؟**
- بهترین کار تعریف request فایل ها می باشد که باعث می شه ما کدهای ولیدیشن و مسیج های اونارو یجا تعریف کنیم و حتی چند جا استفاده کنیم
- کدهای کنترولر کمتر و تمیزتر میشه چون بجای پاس دادن request به متد مورد نظر می تونیم request فایل ها رو پاس بدیم که در صورتی اون متد کنترولر ادامه میدن که ولیدیشن true شده باشه
- حتی می شه داخل این request فایل ها بررسی کرد که حتما این ولیدیشن برای کاربر لاگین شده باید باشه یا نه (متد فک کنم authorize بود)
- دستور تعریفشم php artisan make:request ArticleRequest هستش.
- داخلش میشه تشخیص داد برای کدوم روت می خوایم ولیدیشن بنویسیم که برای هر عملیات مثلا article چند تا فایل تعریف نکنیم (add, updarte, ...)

**رابطه‌های polymorphic رو توضیح بدید.**
فک کنم وقت کم بیارم، کوتاه می گم، چند ریختی! یعنی مثلا تگ رو میشه هم برای article استفاده کرد و هم برای post. نیایم روابط جدا جدا تعریف کنیم.

**فرض کنید نام و نام خانوادگی کاربر در دو فیلد جداگانه در دیتابیس ذخیره می‌شود، برای نشان دادن نام نمایشی کاربر که شامل هر دوی این فیلد‌ها هست از چه امکانی می‌توانیم استفاده کنیم؟**
مثل در مدل User می توانیم بنویسیم:
public function getFullNameAttribute(){
return $this->firstname . ' ' . $this->lastname
}
همان مبحث accessor ها هستش :)

**Query Scopeها را در مدل‌های Eloquent توضیح بدید**
بعضا پیش میاد برای دریافت یکسری رکورد از یک مدل خاص مجبوریم چندین شرط رو پشت سر هم هی بنویسیم.
به عنوان مثال که البته خیلی مثال ساده ای است چند جا در کد کاربران فعال و تایید شده را نیاز داریم که شامل دو where برای فیلد is_active و is_verified می باشد. بجای نوشتن مکرر این where ها در مدل User میایم یه اسکوپ تعریف می کنیم میگیم scopeLiveUser و شرط رو داخل اون میزاریم که هر جا خواستیم به جای اون دو where از این اسکوپ استفاده می کنیم و بعد ادامه ماجرا و ادامه کوئری.

**در پروژه‌هایی که داشتید با Queue در لاراول کار کردید؟ اگر بله توضیحی درباره نحوه استفاده و مساله‌ای که از صف برای حل اون استفاده کردید بدید**
بله انجام دادم، نیاز به برنامه supervisor هم هست که همیشه کامندشو بالا نگر داره. بیشتر برای ارسال اس ام اس و ایمیل استفاده میشه.
مثلا ارسال اس ام اس تایید موبایل میشه یه queue جدا تعریف کرد (از دیفالت جدا بشه با اولویت مخصوص خودش)
مثلا ارسال ایمیل ووچر هتل برای مسافران که اون مثلا اولویتش می تونه از تایید موبایل پایین تر باشه

**کاربرد Resource Collectionsها در لاراول چی هست؟**
در زمان کار با api می شه ازش استفاده کرد و به جای ارسال کل فیلدهای آرایه ای از یه مدل (مثلا کاربران)، فقط فیلدهای خاص رو انتخاب کنیم با کلید مد نظر بفرستیم به سمت کاربر. یا فیلدی بخواهیم خودمون اضافه کنیم. یه جا مرتب منظم توی ریسورس فایل ها تعریف میکنیم.

**با تست‌ها در لاراول آشنا هستید؟ چه نوع تست‌هایی در لاراول داریم؟ برای اجرای تست‌ها از چه دستوری استفاده می‌کنیم؟**
- feature test: برای تست یک فرآیند مثل ثبت نام و ... استفاده می شه
- unit test: برای تست یک واحد خاص مثل یک هلپر، یک ولیدیش و ... استفاده می شه
- browser test: که از ابزار dusk استفاده می کنه می تونیم باهاش بگیم برو فلان صفحه فرمو پر کن فلان اتفاق بیافته
php artisan make:test RegisterTest
php artisan make:test CustomValidationTest --unit

توی هیچ پروژه ای tdd کار نکردم ولی مطالعه و تست داشتم. یسری مباحث ماک و اینا هم داره :)

**متد actingAs در تست‌ها به چه منظوری استفاده میشه؟**
برای لاگین کاربر در محیط تست استفاده می شود

**در یک repository اگه بخواهیم n کامیت به عقب برگردیم بدون اینکه تغییراتمون در لوکال از بین برن از چه دستوری می‌تونیم استفاده کنیم؟**
هد رو دستکاری می کردیم ولی الان حضور ذهن ندارم.

**در مورد Branch و Pull request توضیح بدید.**
برای یک فیچر خاص می توان یک برنچ درست کرد که از flow اصلی جدا بشه و کارو پیش ببریم.
pull request هم برای مثلا وقتی هستش که یه فورک از یه ریپو گرفتیم و تغییراتی رو روی ریپوی فورک شده اعمال کردیم و می خواهیم روی اون ریپوی اصلی (که صاحبش نیستیم) بفرستیم از pull request استفاده می کنیم تا اگر صاب ریپو تایید کرد پول شه بره رو ریپوی طرف

**بعد از ایجاد هر pull request کدهای شما review میشه و بعد وارد branch اصلی میشه. فکر می‌کنین در مرحله review به چه فاکتورهایی باید توجه بشه؟**
به conflict هایی که با مرج کردن بوجود میاد

## مدیریت تسک و فرایند

**در توسعه یک سیستم فروشگاهی تسکی با عنوان «مدیریت برچسب‌ها» به شما محول شده، جزئیات این تسک رو بنویسید. شما باید این تسک رو به کوچک‌ترین واحدهای کاری بشکنید طوری که بتونید هر واحد کاری رو در زمان مشخصی انجام بدید. جلوی هر قسمت از این تسک میزان ساعتی که تخمین می‌زنید انجام اون قسمت طول می‌کشه رو به ساعت بنویسید**
- تعریف مدل مربوطه به همراه تعریف migration و روابط مدل با مدل های دیگر
- تعریف کنترولر و متدهای مربوط به:
1. لیست برچست ها + صفحه بندی + فیلتر
2. اضافه کردن برچست ها
3. ویرایش برچسب ها
4. غیرفعال/فعال کردن برچست ها
5. جزییات هر برچست

**از چه ابزارهایی برای مدیریت کارهاتون استفاده می‌کنید؟ در پروژه‌های قبلی‌تون برای مدیریت ارتباطات بین تیم و مدیریت پروژه از چه ابزارهایی استفاده کردید و باهاش آشنا هستید؟**
متاسفانه در شرکتی که کار کردم اعضای تیم همکاری نمی کردند و فقط یک مدت jira استفاده شد

**با متد اسکرام در مدیریت پروژه آشنا هستید؟ به عنوان عضوی از تیم توسعه تو جلسه‌های استند‌آپ روزانه چه مواردی رو باید توضیح بدید؟**
متاسفانه تجربه کاری به این شکل رو نداشتم
